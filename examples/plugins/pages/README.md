# Pages and host capabilities example

A backend-free plugin package that adds two pages to GoNavi and shows the version-one
page contract: an entry in the title-bar **Plugins** menu, one declarative page, and one
sandboxed HTML page that calls host capabilities through the page bridge.

- Manifest: [gonavi.plugin.json](<gonavi.plugin.json>)
- Contract: [plugin pages, menu and host capabilities](<../../../docs/plugins/pages.md>)
- Permission reference: [permissions](<../../../docs/plugins/permissions.md>)
- SDK: [Go and TypeScript SDKs](<../../../docs/plugins/sdk.md>)

## What it declares

| Declaration | Value |
|---|---|
| Package id | `sdk.examples.pages` |
| Permissions | `ui.pages`, `ui.html-panel`, `host.connections.read`, `host.metadata.read` |
| `pages` | `overview` (declarative body) and `connections` (custom HTML) |
| `navigation` | Both pages at `location: "tools"`, orders 0 and 10 |
| Backend | none |

The package has **no backend executable**. It therefore declares no commands, and
`gonavi plugin invoke` has nothing to call. Once a runtime owner starts it (the desktop app,
or any CLI command that acquires the owner), the host marks such a static package running
without launching a process, so its pages render and the HTML page can use the two declared
`host.*` capabilities.

## Try it

The existing [package builder](<../package/main.go>) copies Skills-only static packages and
builds native backends, so it does not package this page-only example. Inspect and install
the directory itself; it has no executables to build.

Inspect it without executing anything (a disposable plugin root, matching
[development](<../../../docs/plugins/development.md>)):

```sh
work=$(mktemp -d)
gonavi plugin --root "$work/plugin-store" inspect examples/plugins/pages
```

Unlike a native manifest template, this source directory passes inspection directly: the
manifest declares no backend or window entry, so there is no built file to look for.

Install it in the desktop app: **Settings → Plugins → local install**, choose this
directory, review the four permissions and their notes, accept the trust prompt, then
enable `sdk.examples.pages`. With the CLI, install the exact digest the inspection
returned and then persist enable intent:

```sh
gonavi plugin --root "$work/plugin-store" check examples/plugins/pages
gonavi plugin --root "$work/plugin-store" install --digest <digest-from-inspect> --trust examples/plugins/pages
gonavi plugin --root "$work/plugin-store" enable sdk.examples.pages
```

CLI enable writes the same desired state the desktop owner reads; use the desktop for the
actual render check. Disable or remove the example when you are done.

## Open the pages

1. Enable the package and wait until it reports `running`.
2. Open the **Plugins** menu in the title bar and pick **Pages overview** or
   **Saved connections**.
3. The same entries appear on the plugin card under **Settings → Plugins → Open**.
4. Disabling or removing the package leaves an open tab in an unavailable state; the
   bridge stops accepting calls and returns `not_running`.

## Page bridge (HTML pages)

The HTML page gets a version-one runtime with exactly two methods:

```js
const connections = await window.gonavi.call('connections.list');
await window.gonavi.call('metadata.databases', { connectionId: connections[0].id });
window.gonavi.notify('Loaded', 'info');
```

- `window.gonavi.call(method, arguments)` resolves with the host result or rejects with the
  localized failure text. Only registered methods whose permission this package declared
  are dispatchable; everything else fails with `permission_denied` or `unknown_method`.
- `window.gonavi.notify(message, type)` shows a transient in-app message. `type` is
  `success`, `info`, `warning` or `error`.
- The frame is `sandbox="allow-scripts"` with an opaque origin. Its CSP blocks page
  fetch/XHR/WebSocket, external subresources, forms and nested frames, so the page cannot
  use storage or cookies either.
- **The CSP does not stop self-navigation.** The host injects a per-frame token into the
  runtime and drops messages without it. If the iframe loads a second time (the page
  navigated itself away from `srcdoc`), the host unmounts the frame, revokes the bridge and
  shows an unavailable state. Data already received can still leave through that
  navigation, so treat this package and its host data as trusted code.
- Limits: at most 8 concurrent calls, 30 seconds per call, 64 KiB of arguments and 256 KiB
  of serialized result. Calls are limited to 30 per 10 seconds and notifications to 10 per
  10 seconds; over-limit calls fail with the bridge error key. Unmounting the tab discards
  late responses. Do not hand-craft bridge messages: the token is generated by the host.
- Connections are resolved by saved-connection **ID**. The page never receives a username,
  password, SSH or proxy credential, or a DSN. The `readOnly` flag from
  `connections.list` is the connection's effective read-only mode (the connection type
  supports it and the connection is forced read-only), and multi-host connections may have
  an empty `host`/`port`.
- `host.query.read` is not declared here. A package that adds it can run one read-only
  statement with `maxRows` 1..1000 (default 100): the host binds a scan-layer budget of
  `maxRows+1`, so supporting drivers stop reading at the limit and `truncated` becomes true;
  legacy drivers read first and are truncated by the gateway. Result bytes stay capped at
  256 KiB. Read-only is not side-effect free: common locking clauses and
  `nextval`/`setval`/`pg_terminate_backend`/`pg_read_file` are rejected, but other
  functions are not enumerated, and a legacy driver may keep running after the 30-second
  bridge deadline (context-aware drivers are interrupted).

## Why these permissions

`host.connections.read` and `host.metadata.read` are enough to show names, types and
database names without reading rows or running SQL. Add `host.query.read` only when a page
really needs one bounded read-only query, and keep the least-privilege set otherwise.

The package is not an operating-system sandbox and does not need one: all work happens in
the host. Pages are declarations and inert HTML; they only reach the host through the
methods above.
